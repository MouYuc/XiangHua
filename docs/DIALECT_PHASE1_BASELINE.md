## 这一轮要回答什么

用户的训练语料只有普通话，也不可能去学各地方言，所以方言能力必须全部来自平台侧资产。
阶段一固定一个变量：**只问“方言能不能念对”，不问“像不像本人”**。

做法：同一批普通话句子，先用 DiaMoE 自带的 IPA 前端转写成各方言 IPA，再用一段参考音合成，
最后用中文 ASR 回读 + 波形层面的音节数检查。音色不参与结论。

## 听感问题的根因（本轮定位到三条）

最初一版音频听起来「音节丢掉、字念不完整、停顿奇怪」。逐条查下来是三个互相独立的缺陷：

### 1. 参考音自身的停顿被复制进了输出（影响最大）

F5 会延续参考音的韵律，**包括参考音里的静音**。而总时长预算是固定的，于是参考音里那个
1 秒多的停顿会在输出里复现，两侧的音节被挤压掉。

证据（同一句话、同一个参考音，只差“参考音是否去除内部停顿”）：

| 用例 | 原始参考音 | 去停顿后的参考音 |
| --- | --- | --- |
| 普通话对照 probe004 | 最长内部停顿 1.56s，3.04 音节/秒 | **0.30s，4.13 音节/秒** |
| 成都 probe004 | 0.58s | **0.26s** |
| 石家庄 probe004 | 1.24s | **0.57s** |
| 西安 probe004 | 1.10s | **0.46s** |
| 普通话对照 probe002 | 0.91s，CER 0.10 | **0.29s，CER 0.00** |

现在流水线默认会把参考音里超过 0.25s 的内部停顿压到 0.06s（`squeeze_reference_silence`）。
注意这不是“拉长时长”：F5 的 `speed` 拉长反而会让模型开始复读参考音内容，那条路已经验证走不通。

### 2. 采样种子会整段吞掉音节

同一个文本、同一个参考音，换一个种子结果完全不同：

```
putonghua probe002  seed 333 -> 6 个音节核，CER 0.60，开头“老铁稳住”没了
putonghua probe002  seed 1   -> 11 个音节核，CER 0.10
putonghua probe002  seed 2   -> 11 个音节核，CER 0.30
putonghua probe002  seed 4   -> 11 个音节核，CER 0.00   ← 选中
```

这是采样方差，不是模型能力问题。现在每句话渲染 4 个种子（333/1/2/4），按
「ASR 一致度 → 尾部静音 → 最长内部停顿」挑最好的一条，候选全部保留在 `audio/<方言>/candidates/`。

### 3. 官方方言 prompt 的语速是正常人的两倍

DiaMoE 自带的官方 prompt 说得很快（成都 2.55s / 15 音节 ≈ 5.9 音节/秒）。F5 的输出时长是
`参考音帧数 / 参考音 token 数 × 目标 token 数`，所以**参考音多快，输出就多快**。用官方 prompt
当参考音时，16 个音节被压进 2.15s（7.4 音节/秒），音节自然糊在一起。

而方言身份并不依赖参考音（见下方 A/B 组对比），所以现在默认改用用户自己的普通话录音当参考音，
语速回到自然的 3.4~4.7 音节/秒。

## A / B 组：方言由谁决定

同一个方言、同一句话，只换参考音：

| 方言 | 官方方言 prompt 作参考音 | 用户普通话录音作参考音 | MoE 专家是否一致 |
| --- | --- | --- | --- |
| 成都 | 专家 0 | 专家 0 | 一致 |
| 石家庄 | 专家 3 | 专家 3 | 一致 |
| 郑州 | 专家 8 | 专家 8 | 一致 |
| 南京 | 专家 5 | 专家 5 | 一致 |
| 西安 | 专家 5 | 专家 5 | 一致 |
| 上海 | 专家 2 | 专家 2 | 一致 |

参考音里一点方言都没有，MoE 路由和方言产出完全不变。**方言身份来自 IPA 前端 + MoE，参考音只贡献音色。**
这正是项目最核心的假设：用户只提供普通话语料也能说出各地方言。

需要克制解读的一点：南京和西安都路由到专家 5，普通话对照路由到 7，所以**9 个专家不等于 9 种方言**，
不能当方言分类器读；能确定的是路由稳定、且随方言文本变化。

## 本轮无法覆盖

| 方言 | 原因 |
| --- | --- |
| 粤语 | 前端没有粤语词典，无法把普通话文本转成粤语 IPA；项目已有原生 GPT-SoVITS `<yue>` 路径 |
| 天津 | 有官方 prompt，但前端没有天津词典 |
| 闽南语 | `frontend/dialect/gaoxiong/` 只有 syllable/tone 表，缺 hanzi/word 表 |

## 下一步建议（按优先级）

1. **补前端词典**：上海 `这/没/什/尾`、南京 `什`、青岛 `o̯` 映射、郑州少掉的音节。
   这是现在唯一还会真正吞字的环节，也是上海 16 个音节只剩 8 个核的原因。
2. **参考音质量门**：正式流程里要对用户上传的录音做去停顿 + 时长/信噪比检查，
   参考音的停顿会一比一复制到输出里。
3. **候选数提升**：目前 4 个种子，代价是 4 倍算力。后面可以按 CER 预测挑种子，而不是全渲染。
4. **人耳验收**：ASR 对吴语、江淮官话没有判断力，上海/南京必须请母语者听。
   当前基准的 wav 在 `output/dialect_baseline/20260923_224346/audio/<方言>/`。

## 人工偏好分析（正式试听数据）

试听数据：18 组（9 方言 × 2 句）× 4 个候选种子 = 72 条，人工在每组里挑出最好的一条。
标签存在 `assets/dialect_listening_labels.json`，分析脚本 `scripts/dialect_preference_analysis.py`，
输出在结果目录的 `preference.json`。

### 结论一：现在的自动挑选是不能用的

自动规则（ASR 一致度 → 尾部静音 → 最长停顿）与人工选择：

```
一致 2 / 18  = 11.1%
随机猜中概率   = 25%
```

**比瞎猜还差**。而且有三组（南京 002、石家庄 002、青岛 002）人工挑的正是自动规则排名**最差**的那条。
原因很清楚：CER 是拿普通话 ASR 去比对普通话原句，它度量的是「听起来像不像普通话」，
而不是「听起来是不是好的方言」。方言味越足，CER 越高。

代码里已经写明这一点（`SELECTION_NOTE`），`--candidates 1` 加人工指定的种子才是给人听的正确用法。

### 结论二：我们现有的客观指标都不能预测人耳

每组内按特征排序，人工所选的名次平均值（4 个候选，无信息时 ≈ 1.5）：

| 特征 | 平均名次 | 方向 |
| --- | --- | --- |
| trailing_silence | 1.78 | 偏高 |
| nucleus_cv（音节间隔不规整度） | 1.72 | 偏高 |
| energy_cv | 1.61 | 偏高 |
| longest_gap | 1.61 | 偏高 |
| f0_log_std | 1.56 | — |
| nuclei | 1.56 | — |
| modulation_ratio | 1.33 | 偏低 |
| voiced_ratio | 1.33 | 偏低 |
| cer | 1.28 | 偏低 |
| spectral_flatness | 1.06 | 偏低 |
| zero_crossing_rate | 1.06 | 偏低 |

全部挤在 1.06~1.78 之间，没有一条能可靠区分。**时长和语速在各候选之间完全相同**
（F5 的时长由参考音和文本决定，与种子无关），所以它们对挑选零信息量。

### 结论三：种子 333 异常突出，但需要盲测确认

人工选择分布：333 出现 **10/18**，而 4 个候选中随机期望只有 4.5/18（p ≈ 0.002）。
这要么说明种子 333 确实更好，要么说明「文件名里带 333 的那条」影响了判断
（候选文件名是 `..._s333.wav`，听的人知道自己在听哪一条）。

所以在把「固定用 333」写进产品之前，必须先做盲测。已经生成好盲听包：

```
output/dialect_baseline/blind_audition/
  LISTEN.md        听音顺序表
  <方言>_<句>/     01.wav ~ 04.wav（顺序已逐组打乱）
  blind_map.json   答案对照，听完再打开
```

18 个组、每组 4 条，文件名与种子完全解耦，听不出哪条是哪条。
如果盲测后 333 依然明显胜出，就是真实的种子效应，可以固定使用；
如果 333 的优势消失，说明之前是文件名造成的偏差，那就必须走人工挑选或建新的评分模型。

### 结论三（盲测修正）：种子 333 的优势是假的

第一轮试听时候选文件名是 `..._s333.wav`，听的人知道自己在听哪一条。为此做了一轮盲测：
同样的 4 条音频，改名成 `01.wav`~`04.wav`，顺序逐组打乱，听不出对应关系。

| | 选中 333 的次数 | 相对随机期望（4.5/18） |
| --- | --- | --- |
| 第一轮（文件名可见） | **10 / 18** | p = 0.005 |
| 盲测（文件名隐藏） | **5 / 18** | p = 0.48（就是纯随机） |

**结论：没有任何种子系统性地更好，之前的"333 更好"是文件名暗示造成的偏差。** 不能把固定种子写进产品。

代码默认已经从「每句渲染 4 条挑一条」改成 **`--candidates 1`（每句一条）**，因为多渲染 4 倍算力换不来可验证的质量提升。

### 结论四：同一条音频，两次试听的一致性只有 44%

盲测选出的音频与第一轮是同一批，只是呈现方式不同：

```
两轮选中同一条音频：8 / 18 = 44.4%   （随机 25%，p = 0.057）
```

也就是说人耳偏好**只有弱可复现性，没有达到可用的稳定度**。这条很重要，它直接决定了两件事：

- 现在这 18 组标签**不足以训练偏好模型**——训练出来拟合的是噪声。
- 想要可靠的标签，得换协议：同一组重复多次、乱序多轮，只保留每次都一致的组；或者上多个人听。

### 结论五：参考音去停顿顺带修掉了种子敏感问题

修好参考音之前，种子会整段吞音节（seed 333 把"老铁稳住"整段丢掉，CER 0.60）。
现在四个种子的表现在对照组上完全一致：

```
普通话对照 probe004:  seed 333 -> CER 0.000, seed 1 -> 0.000, seed 2 -> 0.000, seed 4 -> 0.000
```

所以那个"吞音节"现象是**参考音里的停顿**引起的，不是种子本身。修在参考音上才对，修在种子上没用。
